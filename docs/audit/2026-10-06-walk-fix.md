# 測定器の周の歩き方の修正（2026-10-06）

対象：tools だけ（`tools/sim.html`・`tools/measure/{bosscamp,campaign,finalcamp,inflation}.js`）。src は触っていない・版は上げていない。
測った版：origin/main c562b42 に上の変更を載せたもの。条件は `finalcamp.js`（HPMUL 2.5・FON true）・`PLACE_MODE 'range'`・測定ごとに `Game.newSave()`・`REAL_MS` 600000・6本ずつ並べた。

## 何が壊れていたか（診断）
- 自動配置はそのときの上限までは置けていた。問題は**上限そのものが12に落ちていた**こと。
- 周の歩き方が、`Game.canSkip` なら必ず `skipStage` していた。スキップは報酬0なので、上限（コインで買う `units`）が育たない。
  転生で第1〜29章を全部飛ばし、収入の無い第30章（雑魚が出ない＝負けてもコイン0）に上限12・5基で挑み続けて永久に詰んでいた（1006l の通しで12本中4本）。

## 変更
1. **周の歩き方**（`reachDistAsync` の `lap`）：スキップするのは `Game.costCap() >= BAL.costBase + 14×BAL.costPerNode`（68）に届いてから。届くまでは前回到達までの章でも戦って稼ぐ。`opts.capSkip=false` で前の歩き方。
   - 理由：スキップは報酬0で、上限はコインで育つ。プレイヤーも上限が育つまで手前の章を回して稼ぐ。「前回到達の5章手前まで飛ばす」案は固定の数字で、上限の育ち具合を見ないので採らなかった。
2. **記録**：`runStage` の返り値に `cap`（そのときの上限）・`used`（置いたコスト）・`n`（基数）・`maxCap`（68）。`lap` が全出撃を `recs` に持ち、`progressAsync` の行に `cap`（`capSummary`：`runs`・`under`（used < cap−2 の出撃数）・`underAt`・`ch30`・`ch30notMax`・`ch30caps`）を足した。ひな形4本は出力に `cap` を含む。
   - 記録は最初の `autoPlace` の直後（出撃の初期配置）の値。ウェーブ間の置き直し（`replaceUnits`）の使用コストは**未測定**。
3. **安全網**：`autoPlaceRange` と `replaceUnits` で `placeUnit` が断った武器があれば、その種類を除いて `costWant(exclude)` を引き直し、浮いたコストをほかの武器に回す（最大4回）。`autoPlaceHug`（比較用の旧配置）には入れていない。

## 注意（読み方）
- **通しの分は前と比べられない。** 上限が最大になるまで手前の章を戦うので、周が長くなり（前より約100分多い）、「第30章に届くまでの時間」を含む別の歩き方になった。分は「前の測定より長くなった」と読む。
- 「第30章を最後まで越えられない 4/12 → 0/12」は、**ゲーム側が良くなったのではなく、測定器が上限12で詰んでいた分が消えた**もの。第30章の本当の難しさは「初回の1回目で突破 10/12・失敗2本は dead w1」。この2本（シード1・10）が上限68・29基なのにウェーブ1で負けた原因は未調査。
- 1本ずつの出撃の揺れ（同じシードでも再現しない）があるので、10/12 という数字は1回ずつの測定。
